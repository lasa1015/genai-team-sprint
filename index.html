Theory background

Friday, quickly: exceptions & collections decks 15 & 13

The exception family. A checked exception (extends Exception) is a business condition callers must face — InsufficientFundsException: the method signature carries throws, and its message names both the requested and the available amount. An unchecked exception (extends RuntimeException) is a bug, not an everyday event — InvalidRateException for a negative rate. Throwing beats warning: a warning scrolls off the screen; a thrown exception stops the wrong thing from happening.

equals / hashCode. A HashSet spots a duplicate in two steps — it asks hashCode() (which bucket?) then equals() (really the same?). Define both from the same fields (here: everything except the re-issued id) and the Set drops re-sends (1005 → 1000). Get them out of sync and the dedupe fails silently — the worst kind of bug. computeIfAbsent builds a grouping Map<Currency, List<Transfer>> in one line.

Unit tests that earn their keep JUnit 5 deck

A unit test isolates one behaviour: arrange, act, assert — one reason to fail. Test names are documentation (method_condition_outcome). Doubles need deltas. assertThrows makes the failure path a first-class citizen: the unhappy path is where money systems earn trust. @BeforeEach rebuilds the fixture so tests stay independent; a test that depends on another test's leftovers will betray you on a Friday. @ParameterizedTest multiplies one behaviour across many inputs without copy-paste.

Mocks: testing conversations Mockito deck

Real dependencies are slow, flaky, or — like RateFeed — don't exist. A mock stands in: when(…).thenReturn(…) scripts its answers (a stub); verify(…) interrogates the conversation (an interaction test): was it called, how often, with what, or never()? State tests ask "what came back?"; interaction tests ask "did we talk to the collaborator correctly?" — the guard-order test is pure interaction: validation must fail before the feed is consulted. Mock what you own the boundary to; don't mock value objects.

TDD: the discipline TDD deck v2

Test-Driven Development inverts the order: the test defines "done" before the code exists. Red — watch the failure, and check it fails for the right reason (a compile error is not a red). Green — the least code that passes; hardcoding early is orthodox, generality is debt until a test demands it. Refactor — with green as your license. The commit log (tdd: rule N green) becomes the audit trail of the design emerging. TDD's real product isn't tests — it's code whose every behaviour was once a requirement someone stated.

AI-generated tests GenAI deck

Given code, a model writes tests that mirror the code — including its bugs; the suite goes green and proves nothing. Given rules, it writes tests that check intent — and can catch the implementation lying. So: generate from specifications, review every assertion, and treat generated tests like a junior's PR — useful, fast, and unsigned until you've read them. Trust, but verify is the whole game.
